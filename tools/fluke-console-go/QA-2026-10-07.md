# Validación de Fluke Console — Windows

## Incremento 2026-10-08: intervención, atención global y seguimiento de PRs

F2 → `m` y F3 → Ctrl+X → `m` abren un editor propio para escribir al worker.
Enter guarda la instrucción antes de enviarla; Shift+Enter agrega una línea y
Esc conserva el borrador. La instrucción entra también en el contexto del
orquestador. `:tell ID | mensaje` ofrece el mismo recorrido por comando.
Una respuesta ya guardada se corrige con F4 → Enter o `:amend N respuesta`:
la corrección referencia a su original sin sobrescribir el historial. No se
reinterpretan propuestas de alcance ni entregas ya integradas/publicadas.

La entrega se serializa por sesión y cada despacho tiene su archivo de mensaje
separado. El contexto del worker se actualiza antes de notificarlo. Una entrega
lista requiere confirmar el número de instrucción humana vigente; un reporte
anterior no vuelve a habilitar revisión después de pedir cambios. La numeración
de decisiones se conserva al filtrar por repo/tarea. Envíos inciertos tras
reinicio requieren intervención y no se repiten solos.

F1 reúne decisiones pendientes, entregas por revisar, pedidos nativos de permiso
y problemas de PRs, incluso de otros proyectos. Enter abre el proyecto y la
tarea/sesión correspondientes. No se presentan sesiones inactivas o trabajando
normalmente como alertas. El texto breve y la ayuda se ajustan al ancho del panel.

Los PRs publicados por Fluke tienen seguimiento de solo lectura de checks,
review y estado remoto. Hay una consulta a la vez, con timeout, tamaño limitado
y al menos un minuto entre consultas automáticas del mismo PR. Ctrl+R permite
actualizar desde F2/F7. Un error conserva el último resultado válido, y una
respuesta tardía de una publicación anterior se descarta. Este estado llega al
orquestador; un merge remoto no certifica integración local ni libera dependencias.

quedaba en su editor sin enviarse. Fluke ahora reconoce el modo de pegado

pegar y usa notificaciones automáticas breves. La repetición real pasó pregunta
→ respuesta → corrección → segundo mensaje directo en la misma sesión. Se
verificó el archivo producido externamente y los acuses de las instrucciones
2 y 3 (141,44 s; paquete 141,538 s).

Las pruebas dirigidas del pegado, instrucciones, decisiones, continuación y

## Incremento 2026-10-08: publicación, historial y arranque recuperable

F7 → `p` permite preparar, editar y confirmar la publicación. El backend crea
un commit de la entrega aceptada si hace falta y publica únicamente su rama
propia, sin force. Un PR nuevo se crea como borrador; uno abierto se actualiza
conservando su estado. El título/cuerpo se revisan antes de escribir. Cambios
concurrentes de referencias, aceptación, metadatos o estado borrador invalidan
la operación. El índice real se comprueba antes del commit para impedir que
archivos internos entren en la publicación. No se incluyen trazas ni rutas
locales absolutas en el cuerpo generado.

La autorización se guarda antes de escribir. Una rama subida no prueba que el
PR esté completo; se consulta el resultado remoto y no se repiten ciegamente
escrituras inciertas. Las pruebas usan repos Git reales temporales y un CLI
GitHub simulado. La publicación real en GitHub queda sin verificar.

El ejecutable Windows, abierto mediante el launcher en ConPTY, pasó F1–F7,
configuración, dos workers, cola, respuesta, revisión/aceptación, edición de

archivos, rama principal intacta durante la publicación, contenido del PR y
registros de integración. Las capturas corresponden a datos de prueba.

Las sesiones guardan base, contrato, estado de ejecución y UUID antes de abrir
el proceso. Una prueba ConPTY comprueba ese estado desde el primer código del
hijo; un fallo de guardado impide abrirlo. El primer mensaje humano se guarda
pendiente antes de iniciar y un envío incierto tras cierre no se repite solo.

Un worktree dependiente viejo puede avanzar con fast-forward al HEAD verificado
del proyecto cuando sigue limpio y no tiene commits propios. No usa reset,

## Incremento 2026-10-08: integración guiada y recuperación nativa

F7 guarda un snapshot de los archivos aceptados y muestra destino, rama y
resumen antes de autorizar commit/merge. Una revisión desactualizada o cambios
en ramas/archivos invalidan la confirmación. El snapshot usa un índice temporal;
la vista previa no modifica el índice real. Los helpers ignorados de Fluke se
excluyen sin excluir archivos de producto con nombres similares.

La intención se persiste antes de mutar Git. Después de crear el commit, se
calcula el árbol del merge y se guarda antes de integrar. Los conflictos
previstos dejan el destino intacto. Se ejecutan los hooks configurados del
repositorio: cambios adicionales en el índice, archivos o commits impiden
certificar el resultado y mantienen bloqueadas las dependencias. Las pruebas
de pre-merge-commit y post-merge pasaron en 18,253 s; conservan los cambios para
revisión. No se hace push, reset, limpieza de ramas ni borrado de worktrees.

Las pruebas Git usan repos temporales y cubren entregas con/sin commit, archivos
nuevos, destino sucio, cambios posteriores a la aceptación, metadata interna,
conflictos, fallos de persistencia y reconciliación tras una interrupción.
Una dependencia también exige que el árbol de su commit siga coincidiendo con
la aceptación; un commit posterior sin revisar ya no libera tareas dependientes.
Si el merge terminó antes de guardar el resultado, se comprueba ascendencia y
árbol esperado sin repetirlo. Un commit adicional de destino antes de esa
reconciliación requiere revisión manual.

Una sesión real Codex pasó pregunta → respuesta → entrega → cierre de la
consola → reapertura → mismo UUID nativo y contrato nuevo → entrega reconciliada
sin repetir la pregunta (96,78 s; paquete 97,427 s). El harness comprueba
result.json y la respuesta previa fuera del relato del modelo. El binding exige
UUID, cwd y nonce de la ejecución inicial en el primer mensaje humano del
transcript exacto; no usa --last ni lee contenido de otras conversaciones.
El formato de ese archivo es interno y se rechaza si no se puede validar.

La ejecución real detectó que PowerShell/cmd recortaba prompts multilínea al
abrir el shim npm de Codex. Las instalaciones npm reconocidas ahora invocan
Node o el ejecutable nativo directamente. Las pruebas verifican Unicode,
comillas, saltos de línea y metacaracteres como argumentos literales; wrappers
desconocidos que no puedan preservarlos piden el ejecutable nativo.

Codex 0.160.1 y Claude 2.1.220 pasaron la comprobación real de versión y sesión
autenticada sin inferencia. Se probó el rechazo de UUID inexistente con ambas
CLIs. La recuperación completa de Claude todavía requiere validación real;

## Incremento 2026-10-08: revisión, pausa individual y dependencias

La pausa individual conserva su intención al reanudar el proyecto. Guardar
primero evita detener procesos si el estado no pudo persistirse. Las respuestas
automáticas también respetan pausas por tarea/proyecto.

Los workers iniciados por la cola conservan el panel y la terminal que usa el
humano. La prueba usa tres PTYs reales: dos arranques de fondo mantienen chat y
foco; un arranque explícito entra al worker elegido.

El despacho de dependientes exige entregas aceptadas, worktrees propios y
limpios, cambios comprometidos y sus commits presentes en el HEAD de destino.
Se comprobó con repos Git temporales: aceptación sin integración bloquea; merge
real libera; un worktree dependiente viejo sigue bloqueado hasta actualizarlo.
También se prueban ciclos, duplicados, otro repo/objetivo, commits vacíos,
archivos sin commit, estado tras reinicio y cola que deja avanzar independientes.
Las comprobaciones Git corren fuera del event loop; se repiten cada cinco
segundos y se revalidan en la preparación. No hacen commit, merge ni push.
Squash/cherry-pick equivalente y dependencias sin cambios requieren otro criterio.

F7 `[c]` pide correcciones al mismo worker mediante el canal existente de
respuestas. El comentario se guarda y se incluye en el contexto del orquestador;
si el worker está cerrado, vuelve a la cola con su worktree y comentario de
arranque. La próxima entrega debe confirmar `review_feedback_seq`: se prueba
que un reporte anterior o sin confirmación no permita aceptar trabajo viejo.

## Comprobado

- Ejecutable Windows por ConPTY: configuración, teclado, dos workers aislados,
  cupo global, vistas, preguntas, respuestas, entregas y cierre.
- Dos repos comparten capacidad; cambiar el foco conserva sesiones y contexto.
- Workers Windows bajo Job Objects: cierre, salida natural del padre y muerte
  de Fluke terminan sus descendientes. Errores de cierre retienen el cupo.
- Guardado atómico, exclusión del estado, recuperación de tareas interrumpidas
  y conservación de archivos corruptos. Los briefs existentes no se pisan.
- Cola con reserva de capacidad, cancelación de un inicio al desencolar y retiro
  de lanzamientos fallidos para evitar reintentos ilimitados.
- Órdenes del orquestador correlacionadas por ejecución y secuencia; aislamiento
  por repo y rechazo de acciones no admitidas. Un ack fallido se reintenta sin
  volver a ejecutar la acción.
- Objetivo/alcance/aceptación sujetos a aprobación, persistidos como spec en el
  repo. La descomposición autónoma exige el ID del objetivo actual; nuevos
  alcances y decisiones de producto pasan por el humano.
- F7 revisa cambios desde la base guardada: commits del worker, staging, cambios
  locales y archivos nuevos. Vista acotada a 256 KiB/200 archivos; base, branch
  y common-dir validados, sin alterar Git.
- Conversación propia: mensajes humanos y respuestas resumidas del orquestador.
  Mensajes de otra ejecución, JSON inválido y estados repetidos se ignoran.
  La CLI completa permanece en F3; las trazas no se proyectan al chat.
- Entrada humana en espera mientras la CLI está ocupada o tiene un diálogo de
  permisos. Revisión bajo el mismo mutex de escritura impide que un aviso
  automático se agregue a un borrador iniciado después de agendarlo.
- Envíos inciertos al reiniciar no se repiten a ciegas. Un fallo de guardado al
  abrir Fluke conserva el primer pedido para revisarlo/reintentar.
- GitHub desde F5/F6: cuenta y device flow, cancelación, tokens por stdin a gh,
  lectura/importación de issues, aislamiento y duplicados. Las pruebas OAuth
  usan un servidor/CLI local. Se verificó antes la lectura real de 23 issues de
  mdevel-uy/fluke; no se hicieron mutaciones remotas.

## Límites conocidos

- La semántica de estar dentro del alcance la resuelve el modelo; el runtime
  valida objetivo, autorización, repo, identidad y cupo, no una equivalencia
  semántica de specs.
- Falta reconciliar specs editadas/intervenciones directas que alteren el encargo.
