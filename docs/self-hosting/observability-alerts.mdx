The observability stack already runs Grafana 13 with its unified alerting engine, which can evaluate rules over the Prometheus and Loki datasources and send notifications natively to Telegram and email. Fleet alerts are provisioned as code from this repository, matching the same "author here, apply on the VPS" pattern used for [logs](/self-hosting/observability-logs), [metrics](/self-hosting/observability-metrics), and dashboards.

<Info>
The stack does not run Alertmanager. Grafana Alerting is used end-to-end: rules, contact points, and notification policies.
</Info>

## What is alerted

Three rules live in the `fluke-fleet` group (folder `fluke`), each evaluated every minute and labelled `proyecto=fluke` so the notification policy can route them to the fleet's contact points without touching alerts from other projects that share the stack.

| Rule UID                     | Fires when                                                                          | `for`  | Severity   |
|------------------------------|-------------------------------------------------------------------------------------|--------|------------|
| `vk-instance-not-reporting`  | An instance's most recent `fluke_build_info` sample is older than 5 minutes.  | `0m`   | `critical` |
| `vk-disk-repos-high`         | Any non-transient filesystem on the instance goes above 80% used.                   | `5m`   | `warning`  |
| `vk-executor-error-rate`     | Sustained rate of failed execution processes above 2/min for 10 minutes.            | `10m`  | `warning`  |

Each alert carries a `runbook` annotation with the first steps to check. Telegram messages include the summary and the runbook inline; the email respaldo carries the full description and runbook.

Rule source of truth: [`ops/observability/alerting/alert-rules.yaml`](https://github.com/mdevel-uy/vibe-kanban/blob/mdev/ops/observability/alerting/alert-rules.yaml) in this repository.

## Contact points

Two receivers, both pointing to the partners' channel:

| Name                    | Type      | Env var(s) for secrets                                    |
|-------------------------|-----------|-----------------------------------------------------------|
| `vk-socios-telegram`    | Telegram  | `VK_TELEGRAM_BOT_TOKEN`, `VK_TELEGRAM_CHAT_ID`            |
| `vk-socios-email`       | Email     | `VK_ALERT_EMAIL_TO` (comma-separated list of recipients)  |

Telegram is the primary channel (push notification on the socios' phones); email is a backup routed by a nested policy so both fire on the same alert. If SMTP is not configured in the stack's `grafana.ini`, leave `VK_ALERT_EMAIL_TO` empty and remove the nested email route in the notification policy.

## Prerequisites

- Grafana 13 with unified alerting enabled (default in the observability stack).
- The Prometheus and Loki datasources reachable in Grafana (already required for the [dashboards](/self-hosting/observability-metrics)).
- A Telegram bot created via `@BotFather`, added as a member of the target group/channel, and the chat ID retrieved from `https://api.telegram.org/bot<TOKEN>/getUpdates`.
- SMTP block configured in `grafana.ini` if the email respaldo is enabled.

## Applying the provisioning (infra task)

The workers of the factory do not have access to the observability VPS. A partner (or Claude in-session on the VPS) copies the provisioning files and reloads Grafana. Every step below is idempotent.

<Steps>
<Step title="Export the contact-point secrets into the Grafana container">
Add the three variables to the observability stack's `.env` (or however the stack passes env vars to the Grafana container):

```env
VK_TELEGRAM_BOT_TOKEN=123456789:AAABBBcccDDDeeeFFFgggHHHiiiJJJkkkLLL
VK_TELEGRAM_CHAT_ID=-1001234567890
VK_ALERT_EMAIL_TO=socio1@mdevel.com,socio2@mdevel.com
```

<Warning>
Never commit these secrets to the repository. The provisioning YAML references them as `$VK_TELEGRAM_BOT_TOKEN`, etc. — Grafana resolves the expansion at load time.
</Warning>
</Step>

<Step title="Copy the rule and contact-point YAML into the stack">
```bash
scp ops/observability/alerting/alert-rules.yaml \
    ops/observability/alerting/contact-points.yaml \
    vps:/docker/observability/config/grafana/provisioning/alerting/
```

Both files are idempotent by `uid`: they only touch the vibe-kanban rules and contact points, leaving anything else in the stack alone.

If the stack's Prometheus and Loki datasources do not use `prometheus` and `loki` as UIDs, edit `alert-rules.yaml` once and adjust the `datasourceUid` fields before copying.
</Step>

<Step title="Integrate the nested notification-policy route">
<Warning>
Do **not** copy `notification-policy.example.yaml` directly. Grafana replaces the entire notification-policy tree when it finds a policies file, which would break routing for other projects on the shared stack.
</Warning>

Instead, edit the stack's existing `notification-policies.yaml` and add a nested route under the root that matches `proyecto = fluke` and routes to `vk-socios-telegram` (with a nested email route). A ready-to-adapt example lives at [`ops/observability/alerting/notification-policy.example.yaml`](https://github.com/mdevel-uy/vibe-kanban/blob/mdev/ops/observability/alerting/notification-policy.example.yaml).

Everything that does not match `proyecto = fluke` keeps falling through to the stack's default receiver.
</Step>

<Step title="Reload Grafana provisioning">
```bash
docker exec observability-grafana kill -HUP 1
```

<Check>
In the Grafana UI, **Alerting → Alert rules** should list the `fluke-fleet` group with three rules, and **Alerting → Contact points** should list `vk-socios-telegram` and `vk-socios-email`.
</Check>
</Step>

<Step title="Verify the acceptance criterion">
Stop a test instance:

```bash
docker compose -f docker-compose.local.yml stop mkanban alloy
```

Within roughly 5 minutes plus one evaluation interval (~6 min total), a Telegram message should arrive:

```
[FIRING · critical] instancia fluke sin reportar métricas
• <cliente>/<instancia> sin métricas hace 6m
```

When the instance recovers and Alloy resumes pushing samples, a `[RESOLVED]` message should arrive shortly after.
</Step>
</Steps>

## Changing or adding rules

Edit the YAML in this repo, not the Grafana UI. Choose a stable `uid` for each new rule (convention `vk-<topic>-<detail>`) so re-provisioning stays idempotent, add a short `runbook` annotation, and label the rule `proyecto: fluke` so it flows through the same notification policy. Then re-apply via the steps above.

## Troubleshooting

<AccordionGroup>
<Accordion title="Grafana loads the rules but no notification arrives when I stop a test instance">
Check the notification policy tree in **Alerting → Notification policies**. If the `proyecto = fluke` route is missing (or falls under the wrong parent), the alert fires but the notification never leaves Grafana. Re-apply step 3 above.
</Accordion>

<Accordion title="Telegram receiver reports `chat not found` or `bot was blocked`">
The bot is not a member of the chat, was removed, or the chat ID is wrong (group chat IDs are negative and start with `-100…`). Re-fetch the chat ID from `https://api.telegram.org/bot<TOKEN>/getUpdates` after posting a message in the group.
</Accordion>

<Accordion title="Email receiver reports `smtp: no such host` or authentication errors">
Grafana's SMTP block is not configured or points to an unreachable server. Fix `grafana.ini`'s `[smtp]` section on the stack and restart Grafana. Until SMTP is fixed, remove the nested email route from the notification policy so alerts still reach Telegram cleanly.
</Accordion>

<Accordion title="`vk-instance-not-reporting` never fires even though the test instance is off">
Check that `fluke_build_info{proyecto="fluke", instancia="<X>"}` is present in Prometheus before stopping the instance. If it is not, Alloy never registered samples in the first place — go back to [Shipping instance metrics](/self-hosting/observability-metrics) and confirm the profile is up.

Also confirm the alert rule is evaluating: **Alerting → Alert rules → vk-instance-not-reporting → Show state history** displays the transitions. If the rule stays `Normal` even with the instance off, the `datasourceUid: prometheus` in the rule does not match the actual UID of the Prometheus datasource in the stack.
</Accordion>
</AccordionGroup>
