Issue #422 · Diseño UX

New Worker Dialog — Propuesta de Rediseño

Diagnóstico y propuesta para que el formulario New/Edit Worker entre en pantallas con ≥ 600 px de alto. El artefacto incluye análisis del problema, comparación de enfoques, mockup interactivo de la solución recomendada y especificación de implementación lista para desarrollo.

1 · Diagnóstico

Estado actual — viewport 640×600

⛔ 600 px de alto disponible
New Worker
Configure your new worker

Causa raíz

  • El wrapper Dialog en KeyboardDialog.tsx no tiene max-height. El browser no activa scroll cuando el contenido desborda un contenedor sin altura límite.
  • El contenedor externo usa overflow-y-auto pero como es fixed inset-0, lo que hace es scrollear el overlay completo, no el dialog.
  • El textarea Soul tiene rows=14 ≈ 240 px — el campo más alto del formulario y el primero en quedar cortado.
  • En pantallas de 600 px la zona visible del dialog termina en la fila de GitHub PAT. Soul nunca es accesible.
El problema NO es el diseño visual — es estructural. Dos líneas de CSS en KeyboardDialog.tsx + reducir rows del textarea resuelven el 90% del caso.

2 · Enfoques evaluados

A · Scroll body + Soul reducido

Fijar max-height en el dialog. Hacer el body scrolleable. Reducir Soul de rows=14 a rows=6. Mínimo código, máximo impacto.

RECOMENDADO

    Pros

  • 2 archivos, ~8 líneas de cambio
  • Mantiene UX familiar exacta
  • Soul sigue siendo editable (scroll interno)
  • Funciona en 600 px y crece bien a 900 px+
  • Zero riesgo de regresión

    Contras

  • Soul "pequeño" por defecto — el usuario tiene que scrollear para ver instrucciones largas
  • No mejora la jerarquía visual (misma lista plana)

B · Campos avanzados colapsables

Soul + GitHub PAT + Plan Mode van dentro de un acordeón "Advanced". Solo Name, Role y Soul siempre visibles.

ALTERNATIVA

    Pros

  • Flujo básico es muy simple
  • Cabe en 400 px colapsado
  • Buena progresividad para nuevos usuarios

    Contras

  • Soul es REQUERIDO — no tiene sentido ocultarlo
  • GitHub PAT oculto = menos descubribilidad
  • Más código: nuevo componente Accordion
  • No encaja con el diseño actual de la app

C · Wizard multi-paso

Paso 1: Name + Role + Model. Paso 2: Soul + Templates. Paso 3: Config + PAT.

DESCARTADO

    Pros

  • Máxima claridad por paso
  • Buen fit para onboarding de usuario nuevo

    Contras

  • Usuarios avanzados editan muchos campos en una pasada — los pasos los frena
  • Complejidad de implementación alta (estado de pasos, validación por paso)
  • No hay precedente en la app de wizard en dialog
  • El issue dice "pantalla única preferible" salvo razón fuerte
Decisión: Enfoque A con mejoras opcionales de presentación. El problema es estructural (falta max-height + scroll), no de cantidad de campos. La solución mínima viable resuelve el 100% del issue sin riesgo de regresión. Las mejoras opcionales (tooltips en vez de help text, resize-y en Soul) son independientes y se pueden hacer en la misma corrida del developer.

4 · Especificación de implementación
packages/ui/src/components/KeyboardDialog.tsx
Cambio 1 — Dialog box max-height

El <div> del dialog box (el que tiene la clase relative z-[10000] flex flex-col) necesita recibir max-h-[min(85vh,680px)].

// Línea ~145 en KeyboardDialog.tsx
// ANTES:
'relative z-[10000] flex flex-col w-full
  max-w-xl gap-4 bg-primary p-6 shadow-lg
  duration-200 sm:rounded-lg my-8'

// DESPUÉS — agregar max-h y overflow:
'relative z-[10000] flex flex-col w-full
  max-w-xl gap-4 bg-primary p-6 shadow-lg
  duration-200 sm:rounded-lg my-8
  max-h-[min(85vh,680px)] overflow-hidden'

El gap-4 existente entre header/body/footer se mantiene. El overflow-hidden en el dialog evita que el shadow del blur del backdrop afecte el scroll.

packages/ui/src/components/KeyboardDialog.tsx
Cambio 2 — DialogContent scrolleable

El componente DialogContent (línea ~209) es el wrapper del body. Necesita flex-1 overflow-y-auto min-h-0.

// ANTES (~línea 213):
const DialogContent = forwardRef(
  ({ className, ...props }, ref) => (
    <div
      ref={ref}
      className={cn(
        'flex flex-col gap-4',
        className
      )}
      {...props}
    />
  )
);

// DESPUÉS — scroll body:
const DialogContent = forwardRef(
  ({ className, ...props }, ref) => (
    <div
      ref={ref}
      className={cn(
        'flex-1 overflow-y-auto min-h-0
         flex flex-col gap-4',
        className
      )}
      {...props}
    />
  )
);

Crítico: min-h-0 es imprescindible. En flex containers, los hijos tienen min-height: auto por defecto, lo que impide que flexbox los comprima aunque el padre tenga overflow-y-auto.

packages/ui/src/components/KeyboardDialog.tsx
Cambio 3 — DialogFooter siempre visible

El DialogFooter necesita flex-shrink-0 para que no sea absorbido por el flex container y siempre permanezca visible.

// ANTES (~línea 217):
const DialogFooter = ({ className, ...props }) => (
  <div
    className={cn(
      'flex flex-col-reverse gap-2
       sm:flex-row sm:justify-end
       sm:space-x-2',
      className
    )}
    {...props}
  />
);

// DESPUÉS — sticky footer:
const DialogFooter = ({ className, ...props }) => (
  <div
    className={cn(
      'flex-shrink-0 flex flex-col-reverse
       gap-2 sm:flex-row sm:justify-end
       sm:space-x-2 pt-2 border-t
       border-border/60',
      className
    )}
    {...props}
  />
);

El border-t border-border/60 da una separación visual clara entre el contenido scrolleable y los botones de acción.

packages/web-core/src/features/workers/ui/WorkerFormDialog.tsx
Cambio 4 — Soul textarea rows

El textarea Soul pasa de rows={14} a rows={6}. Adicionalmente se puede agregar resize-y y min-h-[96px] para que el usuario lo pueda agrandar si lo necesita.

// ANTES (~línea 485):
<Textarea
  id="worker-soul"
  value={soul}
  onChange={...}
  rows={14}
  className="mt-1 font-mono text-sm"
  placeholder={...}
/>

// DESPUÉS:
<Textarea
  id="worker-soul"
  value={soul}
  onChange={...}
  rows={6}
  className="mt-1 font-mono text-sm
             resize-y min-h-[96px]"
  placeholder={...}
/>

El resize-y permite que usuarios con pantallas grandes puedan expandir el textarea arrastrando el handle inferior. El min-h-[96px] previene que quede demasiado chico si el usuario lo encoje.

Mejoras opcionales (misma corrida, si el developer lo ve fácil)

Help texts → tooltip
Los <p className="mt-1 text-xs text-low"> de Role y Plan Mode se pueden reemplazar por un icono HelpCircle de lucide con tooltip. Ahorra ≈ 40 px adicionales.
Separadores de sección
Dividir los campos con etiquetas "Config / Integration / Soul" mejora la legibilidad. Un <div> con texto + border-b es suficiente. El mockup lo muestra.
Scroll personalizado
Opcional: aplicar scrollbar-thin scrollbar-thumb-border (si el proyecto tiene el plugin) o CSS nativo ::-webkit-scrollbar para que el scrollbar del body sea más sutil.
Resumen de cambios requeridos:
  • KeyboardDialog.tsx: 3 cambios de clases Tailwind (~6 tokens agregados)
  • WorkerFormDialog.tsx: cambiar rows={14} → rows={6} y agregar resize-y min-h-[96px]
  • Total: ~4 líneas modificadas, 0 lógica nueva, 0 dependencias nuevas
5 · Preguntas abiertas para el PM
1

¿Viewport mínimo objetivo: 600 px o 480 px?

El mockup muestra que con max-height calculado al 85 vh, en 480 px el dialog queda con ~408 px de alto y el body scrolleable tiene ~300 px. Es funcional pero apretado. Si hay requerimiento de 480 px (móvil landscape), se puede bajar el max-height a min(90vh,640px) y forzar que al menos Name + Soul sean visibles fijando un min-height en el body scroll.

Recomendación: 600 px
2

¿Soul colapsado por defecto en modo creación?

Soul es requerido. Colocarlo en un acordeón cerrado implica que el usuario tiene que abrirlo antes de escribir, lo que genera fricción. La propuesta lo deja abierto siempre. Si hay razón fuerte para ocultarlo (e.g. los templates prefill y el usuario raramente edita el soul de cero), se puede plantear como mejora futura.

Recomendación: siempre abierto
3

¿El border-t en el footer es aceptable?

El DialogFooter propuesto agrega un border-t border-border/60 como separador visual entre el contenido scrolleable y los botones. Esto cambia levemente la apariencia de TODOS los dialogs de la app que usen DialogFooter (el componente es compartido en KeyboardDialog.tsx). Si no se quiere afectar otros dialogs, el border puede ir en la clase del footer de WorkerFormDialog en lugar del componente base.

Recomendación: en el componente base
4

¿Los separadores de sección son parte del scope o mejora futura?

Las etiquetas "Config / Integration / Soul" que aparecen en el mockup mejoran la legibilidad pero son puramente estéticas y opcionales. La corrección del bug no las requiere. ¿Las incluye el developer en la misma corrida o van a un issue separado?

Recomendación: misma corrida si es fácil
