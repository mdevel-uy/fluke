Barra de tabs del Asistente sin scroll, con dropdown de misiones abiertas

Spec del issue #648. Reemplaza el overflow-x-auto de MissionTabs (packages/web-core/src/features/director/ui/DirectorPanel.tsx) por una barra de ancho fijo en tres zonas: Missions fija a la izquierda, una franja con las tabs que entran (la activa siempre entre ellas) y, a la derecha, el botón de desborde con la lista de todas las tabs abiertas y el + de nueva misión. Ninguna zona tiene scroll. El mock usa el mismo algoritmo que hay que implementar (sección 3): cambiá el ancho y la cantidad de tabs.

3. Qué tabs se muestran sueltas (decisión)

Orden de apertura estable, con la activa siempre visible en el último lugar. Se muestran las primeras tabs de openMissionIds (el store ya las guarda en orden de apertura) hasta llenar la franja. Si la activa no está entre ellas, ocupa el último lugar visible y las demás no se mueven. Es un cálculo de render: el store no cambia y el orden persistido sigue siendo el de apertura.

Por qué así y no "las más recientes" (MRU): si las tabs se reordenan cada vez que el usuario cambia de una a otra, la que estaba bajo el cursor se mueve y se pierde la memoria espacial ("billing es la segunda"). Con orden estable, al elegir una tab oculta solo cambia el último lugar. Costo: una tab muy usada pero abierta temprano puede quedar visible y otra igual de usada quedar oculta. El dropdown cubre ese caso.

// Medidas de la sección 2.
const TAB_MIN = 96, GAP = 2, OVERFLOW_W = 44;

/** `width` = ancho medido de la zona (franja + botón de desborde). */
function layoutTabs(ids: string[], active: string, width: number) {
  const fit = (w: number) => Math.floor((w + GAP) / (TAB_MIN + GAP));
  if (fit(width) >= ids.length) return { visible: ids, hidden: [] };
  const k = Math.max(1, fit(width - OVERFLOW_W - GAP)); // reserva el botón
  let visible = ids.slice(0, k);
  if (ids.includes(active) && !visible.includes(active))
    visible = [...ids.slice(0, k - 1), active];
  return { visible, hidden: ids.filter((id) => !visible.includes(id)) };
}
  • Sin oscilación: es una función pura del ancho de la zona, que no cambia cuando aparece o desaparece el botón de desborde (el botón vive adentro de la zona y su ancho ya está descontado).
  • Mínimo 1: si no entra ni una tab de 96px (zona < 142px, por ejemplo un panel de unos 250px), igual se muestra una (la activa, o la primera) con min-w-0, truncada. La activa nunca queda oculta.
  • Activa = Missions: se muestran las primeras k sin forzar nada.
  • Test: layoutTabs es pura; un test unitario con 1/5/20 ids y anchos 150/250/1100 cubre el criterio de aceptación sin DOM.

4. Dropdown de tabs abiertas

Se arma con DropdownMenu de @vibe/ui/components/DropdownMenu (Radix), igual que features/source-control/ui/GraphBranchFilter.tsx: DropdownMenuContent align="end" con max-h-80 overflow-y-auto. Lista todas las tabs abiertas, no solo las ocultas, en el mismo orden que la barra: así cualquier tab se encuentra en un único lugar.

Por quéEn el panel angosto importa más poder leer el título que el repo, y en una línea entran 10 filas en max-h-80 sin scroll. En la vista expandida sobra ancho, y el repo distingue misiones con títulos parecidos. Cómo se elige la variante: el componente ya sabe la vista por useDirectorStore(s => s.view) === 'expanded'.

Contenido de cada fila

  • Check (CheckIcon size-icon-2xs text-brand) en la tab activa, con un slot de 12px reservado en todas las filas. El título de la activa va en font-medium text-high.
  • Indicadores a la derecha del título, exactamente los de MissionsList: punto bg-warning si isWaitingForUser(m), y SpinnerIcon size-icon-xs animate-spin text-low si m.agent_running. Pueden aparecer los dos.
  • X de cerrar siempre visible en el menú, sin depender del hover: en touch es la única forma de cerrar una tab oculta. Usar onPointerDown/onClick con e.preventDefault(); e.stopPropagation() para que no dispare el onSelect del ítem y el menú siga abierto, así se pueden cerrar varias seguidas. Si al cerrar ya no quedan ocultas, el trigger se desmonta y el menú se cierra.
  • Click en la fila (onSelect): setActiveTab(id) y el menú se cierra. Si la tab estaba oculta, pasa al último lugar visible (sección 3).
  • Sin título de grupo ni acciones extra ("cerrar todas", etc.): quedan fuera del alcance (ver preguntas abiertas).

Accesibilidad

  • Trigger: aria-label y title = t('director.openTabs', {count}) (clave nueva, en: "{{count}} more open missions"). Si hay ocultas esperando: t('director.openTabsWaiting', {count, waiting}) ("… ({{waiting}} waiting for you)"), porque un punto de color solo no lo anuncia un lector de pantalla.
  • Teclado: Radix resuelve flechas, Home/End, typeahead, Enter y Esc, y devuelve el foco al trigger. Además, Delete/Backspace sobre un ítem enfocado cierra esa tab (onKeyDown del ítem).
  • La X del ítem lleva aria-label={t('director.closeTab', {title})} (hoy la X de Tab dice "close" fijo; conviene usar la misma clave en los dos lugares).
  • No hay colores nuevos: se usan los tokens existentes (text-low, bg-warning, text-brand).

6. Alternativas descartadas

  • Scroll horizontal con la scrollbar oculta y flechas: saca la scrollbar fea, pero la activa puede quedar fuera de vista y las flechas son lentas con 20 tabs. Para cumplir "la activa siempre visible" haría falta además lógica de scroll-into-view.
  • Solo Missions + activa + dropdown: es más simple, pero en la vista expandida desperdicia todo el ancho y obliga a abrir el menú para alternar entre dos misiones.
  • MRU (las más recientes visibles): ver sección 3.
  • Tabs con ancho según el título: aprovecha mejor el espacio, pero obliga a medir cada tab y la barra salta cuando cambia un título.

7. Preguntas abiertas (no bloquean la implementación)

  • ¿Agregar "Cerrar las demás" o "Cerrar todas" al pie del menú? No está en el brief y queda fuera.
  • Al cerrar la tab activa, ¿ir a la tab vecina en vez de a Missions? Hoy va a Missions y esta spec no lo cambia.
  • ¿Cerrar automáticamente las tabs de misiones en done? Con el dropdown deja de ser urgente.
