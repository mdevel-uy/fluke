UI/UX Design Spec #442 · Worker "In Review" visual state

Estado visual "En revisión" — WorkerCard, WorkerDetailCard, WorkersPage

Propuesta de diseño para el estado review en los tres componentes. Depende de #441 (campo hasTaskInReview en SidebarWorkspace). Los workers cuya tarea está en in_review deben mostrar un indicador diferenciado — azul estático — reservando el rojo para bloqueos reales.

1. Sistema de colores del dot — estado actual vs propuesto

El dot de 8 px en el header de WorkerCard y el dot de 7 px en WorkerDetailCard representan el estado operativo del worker. Hoy el sistema tiene 4 tonos; proponemos añadir review como quinto tono.

Decisión de color: bg-info (#0284C7 light / #38BDF8 dark) en lugar de bg-brand-on-surface opacity-70 sugerido en el brief. Razones: (a) info ya es un token semántico en el design system para estados informativos/en curso sin urgencia; (b) usar opacity-70 sobre brand-on-surface crea ambigüedad visual con el dot "running" pulsante; (c) azul cielo vs azul índigo son fácilmente distinguibles entre sí y con el resto de tonos. El dot review es estático (sin animate-pulse) para indicar que no hay proceso corriendo.

5.2 WorkerDetailCard.tsx — nuevo estado 'review'

// 1. Tipo ampliado
export type WorkerCardState = 'running' | 'review' | 'attention' | 'idle';

// 2. Mapeo dot tone
function cardDotTone(state: WorkerCardState): DotTone {
  if (state === 'running')   return 'run';
  if (state === 'review')    return 'review';
  if (state === 'attention') return 'warn';
  return 'idle';
}

// 3. Borde del card
className={cn(
  'mx-2.5 mt-2 mb-2 rounded-lg border bg-panel px-2.5 py-2',
  state === 'attention' ? 'border-warning/45'
  : state === 'review'    ? 'border-info/45'
  : 'border-border'
)}

// 4. Footer label
const footer =
  state === 'attention'
    ? (attentionLabel ?? t('workspaces.aside.needsAttention', ...))
  : state === 'review'
    ? t('workspaces.aside.inReview', { defaultValue: 'In review' })
  : state === 'running'
    ? [t('workspaces.aside.working', ...), elapsed].filter(Boolean).join(' · ')
  : t('workspaces.aside.workspaceIdle', ...);

// 5. Botón de acción (footer)
// review: sin Stop. Mostrar "Start task" solo si onStart disponible.
{state === 'running' && onStop ? (
  <button onClick={onStop}>Stop</button>
) : state !== 'running' && onStart ? (
  <button onClick={onStart}>Start task</button>
) : null}
// (el state !== 'running' ya cubre 'review', 'attention', 'idle')

5.4 WorkersPage.tsx — stalled fix + inReviewWorkerIds

// stalledWorkerIds: añadir guard task.status === 'in_progress'
const stalledWorkerIds = useMemo(() => {
  const workspaceById = new Map(workspaces.map((ws) => [ws.id, ws]));
  const stalled = new Set<string>();
  for (const worker of workers) {
    if (!worker.active_workspace_id) continue;
    const task = activeTaskByWorkerId.get(worker.id);
    const ws   = workspaceById.get(worker.active_workspace_id);
    if (
      task &&
      task.status === 'in_progress' &&   // ← FIX: excluye in_review
      ws &&
      !ws.isRunning &&
      !ws.hasPendingApproval &&
      !ws.hasTaskInReview &&             // ← FIX: excluye tasks en review
      ws.latestProcessStatus !== 'running'
    ) {
      stalled.add(worker.id);
    }
  }
  return stalled;
}, [workers, workspaces, activeTaskByWorkerId]);

// inReviewWorkerIds: nuevo conjunto basado en hasTaskInReview (de #441)
const inReviewWorkerIds = useMemo(() => {
  const workspaceById = new Map(workspaces.map((ws) => [ws.id, ws]));
  const inReview = new Set<string>();
  for (const worker of workers) {
    if (!worker.active_workspace_id) continue;
    const ws = workspaceById.get(worker.active_workspace_id);
    if (ws?.hasTaskInReview && !ws.hasPendingApproval) {
      inReview.add(worker.id);
    }
  }
  return inReview;
}, [workers, workspaces]);

// Pasar la prop a WorkerCard
<WorkerCard
  worker={worker}
  needsAttention={stalledWorkerIds.has(worker.id)}
  inReview={inReviewWorkerIds.has(worker.id)}
  ...
/>

5.5 Derivar WorkerCardState desde WorkersPage → WorkerDetailCard

// En el contexto que llama WorkerDetailCard, derivar el state:
function deriveWorkerState(
  ws: SidebarWorkspace | undefined,
  isStalled: boolean
): WorkerCardState {
  if (isStalled)                  return 'attention';
  if (ws?.hasPendingApproval)     return 'attention';  // sad path: approval > review
  if (ws?.hasTaskInReview)         return 'review';
  if (ws?.isRunning)              return 'running';
  if (ws)                         return 'running';   // workspace exists pero sin proceso
  return 'idle';
}

8. Preguntas abiertas para el PM / dev

Q1 — ¿Dónde se deriva el estado para WorkerDetailCard?
WorkerDetailCard vive en el aside del shell y recibe state: WorkerCardState como prop. El issue no especifica qué componente llama a WorkerDetailCard ni cómo obtiene ws.hasTaskInReview. El spec de deriveWorkerState() en §5.5 es una propuesta — confirmar si el componente llamador ya tiene acceso al workspace via hook o si hay que propagarlo.
Q2 — WorkersSidebar también usa needsAttention / inReview?
WorkersPage.tsx pasa attentionWorkerIds={stalledWorkerIds} a WorkersSidebar. ¿Debe WorkersSidebar recibir también inReviewWorkerIds para mostrar el dot de review en la lista lateral? No está en el territorio del issue #442 pero es una inconsistencia visual potencial.
Q3 — ¿El badge "In review" en WorkerCard debe mostrar el número de PR?
Si ws.prNumber está disponible en el mismo workspace, podría mostrarse como "In review · PR #123" para contexto adicional. ¿Conviene? ¿O mantenerlo minimal?
Q4 — ¿Qué pasa si #441 no fue mergeado cuando se implementa #442?
hasTaskInReview no existe en SidebarWorkspace todavía (verificado en el hook actual). La implementación debe usar la misma técnica de "extended type cast" que ya se usa para plan_mode y pr_mergeable en el codebase — o bloquear este issue hasta que #441 esté merged.
